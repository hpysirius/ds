# ds-browser-agent

用**你自己的 Chrome**（真实登录态、真实指纹、带插件），像正常用户一样完成核价里最麻烦的那一步：**拿 Ozon 商品图 → 去 1688 找同款 → 抓价 → 算价 → 生成定价记录**。

---

## 为什么是「连你自己的 Chrome」而不是新装一个浏览器

| 方式 | 登录态 | 被 1688 风控识别的概率 | 结论 |
|---|---|---|---|
| 新装 headless 浏览器 | ❌ 没有 | **极高**（无头特征明显） | 走不通 |
| 纯 HTTP 接口调用 | ✅ 有 cookie | 高（重放检测，实测第 2 次就被拒） | 不稳定 |
| **连你自己的 Chrome（CDP）** | ✅ 现成的 | **低**（就是真浏览器、真用户） | ✅ 采用 |

核心就一句：**最难的那一步（图搜）交给真实浏览器，剩下能算能存的全交给 ds 后端 API。**
人在关键节点做判断（挑哪个是同款、过验证码），机器做重复劳动。

---

## 一、启动（每次用之前做一次）

Chrome 必须带调试端口启动，否则 agent 连不上。**关键是完全退出 Chrome**（⌘Q，不是关窗口），然后：

```bash
open -a "Google Chrome" --args --remote-debugging-port=9222
```

> ⚠️ **不要加 `--user-data-dir`**。加了会用全新配置目录，登录态和插件全丢，等于白干。
> 这个方式启动的 Chrome 就是你平时用的 Chrome，书签、插件、登录态都在，只是多了个调试端口。

启动后自检：

```bash
cd scripts/browser-agent
node src/agent.mjs doctor
```

会依次检查：ds 后端是否在线 → Chrome 是否连上 → 1688 是否登录 → ds token 是否可读。

## 二、用法

```bash
# 完整流程：取图 → 1688 图搜 → 人工挑 → 抓价算价 → 生成定价记录
node src/agent.mjs find --sku 3920720492 --apply

# 只找同款，不写库（拿到链接自己处理）
node src/agent.mjs find --sku 3920720492

# 非交互图搜（给网页/后端调用）：结尾打印 @@RESULT@@<json>，绝不卡 stdin
node src/agent.mjs candidates --sku 3920720492


# 用本地图片搜（不依赖 ds 商品）
node src/agent.mjs find --image /path/to/pic.jpg

# 指定售价（人民币），不指定则用商品当前售价换算
node src/agent.mjs find --sku 3920720492 --apply --sell-price 33.77

# 自检
node src/agent.mjs doctor

# 打开某页并截图（调试用）
node src/agent.mjs shot --url https://detail.1688.com/offer/1087462856119.html
```

### 网页端一键核价（无需终端）

ds 定价工作台新增「浏览器 Agent 一键核价（图搜）」卡片：

- 点「开始图搜」→ 后端 `POST /agent/find` 拉起本 agent 的 `candidates` 子命令，驱动本机 Chrome 打开 1688 图搜、上传商品主图、解析候选；
- 前端把候选同款列成卡片，你**点一下**挑真同款（替代原 CLI 的终端 stdin 人工挑选）；
- 点「选这个并核价」→ 后端 `POST /agent/apply` 复用现有 `fetchOffer + calc + createRecord` 抓价/算价/落库，并把结果预填回工作台。

> 前置：仍要连**你自己的 Chrome**（9222）。点按钮前先确认 Chrome 已用
> `open -a "Google Chrome" --args --remote-debugging-port=9222` 启动，否则 `/agent/doctor` 会提示未就绪。
> `candidates` 是非交互模式：1688 未登录或触发滑块会**直接报错**（不再卡住等回车），由网页提示你去浏览器处理。

### 跑起来之后会发生什么

1. **自动**：从 ds 取商品信息（标题/现价/尺寸）→ 下载主图（经 ds 图片代理，绕开 Ozon 防盗链）→ 转成 jpg
2. **自动**：打开 1688 图搜页；若浏览器没登录 1688，**自动把 ds 里存的 cookie 注入进去**
3. **自动**：上传图片、滚动加载、解析候选商品
4. **你来做**：终端会列出候选（价格 / 标题 / offerId），输入序号挑一个
5. **自动**（加了 `--apply`）：抓 1688 价格+重量 → 调 ds 算价 → 生成定价记录

遇到验证码 / 登录失效时，agent 会**停下来**，在终端提示你处理，处理完按回车继续 —— 不会硬闯。

## 四、设计要点

### 「像人一样」的几个细节

- 点击前先**滚动进视口**，停顿一下再点；点击位置在元素的 30%~70% 区间随机，**不总点正中心**
- 鼠标**分步移动**过去（8~20 步），而不是瞬移
- 输入是**逐字符**敲的，带 60~200ms 随机间隔
- 结果列表会**随机滚动浏览**几屏，触发懒加载
- 各步骤之间统一走 `humanPause()`，随机 0.6~1.8 秒

### 登录态从哪来

- **1688**：优先用浏览器现有的；没有就自动注入 ds 库里存的 cookie（`ALI1688_COOKIE` 环境变量可覆盖）
- **ds**：直接从浏览器 `localStorage.ds_token` 读；也支持 `DS_TOKEN` 环境变量
  - 顺带一提：token 来源决定后端地址 —— 从 `localhost:3100` 来的打 `localhost:3101`，从线上域名来的打线上 `/api`，避免跨环境 401

### 为什么尺寸用 ds 商品自带的，而不是 1688 的

1688 那个 offer 的包装尺寸字段全是 `0.0`（卖家没填），抓过来是空的。
所以尺寸回落到**商品在 ds 里已有的尺寸**（如 `29.9×20.1×20.1`），比拍脑袋填 `20×20×20` 靠谱。
重量则优先用 1688 抓到的真实值。

## 五、已知限制（重要）

1. **1688 图搜本身仍有风控**。用真实浏览器能大幅降低被拦概率，但**不能保证 100% 成功**。失败时 agent 会停在候选人机交互那一步，你可以：
   - 在浏览器里手动滚一滚 / 重新上传
   - 或直接用页面上的结果，手动复制 offer 链接
2. **无头环境（headless / CI）不要指望它能图搜**。实测在 headless 里 1688 图搜返回「这里空空如也」，这也是本方案坚持用真实 Chrome 的原因。
3. **dom 结构变化会导致解析失败**。`extractOffers()` 是按 `a[href*="detail.1688.com/offer/"]` 抓的，比较稳，但 1688 改版后可能需要调整。
4. **默认写 `storeId=1`**。多店铺场景要按需改（`applyToDs` 里的 `?storeId=1`）。
5. **不修改 ds 产品代码**。这是本机的运营辅助工具，独立在 `scripts/` 下，不影响线上系统。

## 六、排错

| 现象 | 原因 / 处理 |
|---|---|
| `连不上 Chrome 调试端口` | Chrome 没带 `--remote-debugging-port=9222` 启动。⌘Q 完全退出后按上面命令重启 |
| 连上了但 1688 显示未登录 | cookie 过期了。在浏览器里手动登录一次 1688，之后 agent 会记住 |
| `没找到 ds 登录 token` | 先在浏览器打开并登录 ds（localhost:3100 或线上域名），或设 `DS_TOKEN` 环境变量 |
| 图搜返回「空空如也」 | ① 在真实 Chrome 里重试；② 换张更清晰的主图；③ 手动在页面上传一次 |
| 卡在「需要你手动处理」 | 这是设计行为。去浏览器里处理完，回来按回车即可；输入 `q` 放弃 |
| 看某一步发生了什么 | 查 `shots/` 目录，每步都有截图 |
