## 1688 以图搜图可行性实测（重要，2026-10-07）
用户问「能否借助 WorkBuddy 自动实现：图片 → 1688 找商品」。已完整反编译 + 实测，结论：**接口链路可程序化跑通，但风控严重，只能做低频/人工触发的半自动，不能做稳定全自动。**
- **登录态**：`ds.pricing_settings.ali1688Cookie`（2026-09-20 同步，31 个）**仍然有效** —— `curl https://www.1688.com/` 首页 JSON 里能读到 `"loginId":"tb0498437_11"`。
- **图搜入口**：`http://s.1688.com/youyuan/index.htm?tab=imageSearch` → 302 → **`https://air.1688.com/kapp/1688-search/pc-image-search/?tab=imageSearch`**（SPA）。JS bundle 在 `https://g.alicdn.com/1688-search/pc-image-search/0.0.28/js/{213,p_index,main,490}.js`。
- **第一步 图片上传（实测成功，未触发滑块）**：MTOP 签名协议，`appKey=12574478`，接口 `mtop.relationrecommend.wirelessrecommend.recommend` v2.0，域名 `https://h5api.m.1688.com/h5/<api>/2.0/`，`dataType=jsonp&type=originaljson`，
  data = `{"appId":"32517","params":JSON.stringify({searchScene:"imageEx",interfaceName:"imageBase64ToImageId","serviceParam.extendParam[imageBase64]":<base64>,subChannel:"pc_image_search_image_id"})}`
  → 返回 `{"data":{"imageId":"1415108852570976718","success":true},"ret":["SUCCESS::调用成功"]}`。
- **签名机制**：cookie jar 两步握手（`-b jar -c jar`）。先空请求让服务端下发 `_m_h5_tk`，取 `_` 前缀为 tokenA，`sign = md5(f"{tokenA}&{t毫秒}&{appKey}&{data}")`。**手动拼 `Cookie:` 头会报 FAIL_SYS_TOKEN_EMPTY，必须用 cookie jar。**
- **坑**：base64 塞 URL 会 `header field too large`（24KB 失败）→ 图片要压到 ~4KB base64（sips `-s formatOptions low -Z 160`）才发得出去。
- **第二步 imageId → 商品列表**：同一个 mtop 接口，`params` 换(JSON)：`{method:"getOfferList",searchScene:"pcOfferSearch",imageId:"<id>",beginPage:1,pageSize:60,verticalProductFlag:"pcmarket",charset:"GBK"}`。**首次返回 code:200 且有真实 OFFER 数据；但紧接着重复同样请求返回 `FAIL_SYS_ILLEGAL_ACCESS::非法请求`** → 风控生效，不可稳定复现。
- **风控是账号级的**（用的是真实店铺账号 tb0498437_11），滥用有封号/触发滑块风险。
- **结论/建议**：① 不要做无人值守全自动；② 可行的是「人工点一次 → 后端单次尝试 → 拿到 Top N 给人挑 → 人选中 offerId → 拼 `https://detail.1688.com/offer/{id}.html` → 复用现有 `POST /pricing/sourcing/offer` 抓取回填」；失败时回落到现在的手动流程。这仍落在既有边界（人工触发/单次/有明确 URL）内，加任何更激进的自动化前需用户拍板。

## browser-agent：CDP 驱动真实 Chrome 做核价（2026-10-07 落地）
用户要求「写一个 agent 能自己控制浏览器，像正常用户一样完成核价」。已实现 **`scripts/browser-agent/`**（独立工具，**不改 ds 产品代码**）。
- **技术选型（关键结论）**：连**用户自己的 Chrome**（CDP，`puppeteer-core` 的 `connect({browserURL:'http://127.0.0.1:9222'})`），而不是新装浏览器/纯接口。理由：① 现成登录态+插件+真实指纹，风控识别率最低；② 纯 HTTP 调 mtop 图搜第 2 次就被拒（见上）；③ headless 实测图搜直接返回「空空如也」。启动：`open -a "Google Chrome" --args --remote-debugging-port=9222`（**必须 ⌘Q 完全退出 Chrome 后再启**；**绝不能加 `--user-data-dir`**，否则登录态/插件全丢）。
- **文件**：`src/agent.mjs`(CLI: doctor/find/shot)、`src/browser.mjs`(连接+真人化操作+观测)、`src/tasks/find1688.mjs`(图搜+回填)、`test-ds-chain.mjs`(ds 侧 dry-run 自测)、`README.md`。依赖仅 `puppeteer-core`（不下载 Chromium）。
- **真人化**：点击前 scrollIntoView+停顿、点击位置取元素 30%~70% 随机点、鼠标分步移动、逐字符输入、随机滚动、步骤间 `humanPause(600~1800ms)`。
- **人在回路**：`waitForHuman()` 遇验证码/登录失效时暂停等人在终端按回车（输入 q 放弃），不硬闯。
- **登录态**：ds token 直接读浏览器 `localStorage.ds_token`（且**由来源推导 API base**：localhost:3100→3101，线上域名→域名/api，避免跨环境 401）；1688 未登录时自动注入 ds 库里的 cookie（`ALI1688_COOKIE` 可覆盖）。
- **实测结果**：✅ 连真实 Chrome / 导航 / 截图；✅ 取商品信息（343₽、29.9×20.1×20.1cm）；✅ 下载主图（Ozon 是 **webp**，经 ds 图片代理 → `sips` 转 jpg）；✅ **自动注入 31 个 1688 cookie 后登录态恢复**；✅ 上传图片无报错；❌ headless 下图搜返回空（已确认是 headless 限制，非代码问题）；✅ **ds 侧链路完整跑通**（dry-run）：抓 1688 ¥11.32/274g → 算价 GUOO Economy Extra Small·陆运 运费 **¥11.07**（与用户截图一致）→ 载荷含 `shippingFee`/`billWeightKg`（避免运费存 0）。
- **本次踩的坑**：① `POST /pricing/calc` **不接受 `markupRate`**（settings 里有该字段但 DTO 无，传了报 400 `property markupRate should not exist`）；② `sellPriceRub` 会被后端映射为响应里的 `valueRub`；③ `calc` 返回 `{input,total,available,best,list}`，`best.shippingFee/billWeightKg/grossProfit/profitRate` 就是要存的值；④ zsh 里 `VAR=x cmd1 | cmd2` 的 prefix 赋值**不作用于管道后的 cmd2**，要给 node 传环境变量必须 `export` 或写成 `... | VAR=x node`；⑤ 测试用的 headless Chrome 会占 9222，**测完必须 kill**（`lsof -ti:9222 | xargs kill`），否则用户按 README 启真实 Chrome 会冲突。
- **尺寸策略**：1688 该 offer 包装尺寸全 0.0（卖家没填）→ 回落到 ds 商品自带尺寸（比插件兜底的 20×20×20 准）；重量优先用 1688 真实值。
- **已知限制**：1688 图搜仍有风控，用真实浏览器能大幅降低但不能保证 100%；默认 `storeId=1`；不修改 ds 产品代码。`.gitignore` 已加 `scripts/browser-agent/shots/`。
