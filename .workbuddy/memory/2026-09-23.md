# 2026-09-23

## 插件"连不上后端"排查（Chrome 142+ LNA）
- 现象：插件报"连不上后端"，但后端 3101 活着，curl 带 chrome-extension Origin + PNA 预检全通过。
- 结论：Chrome 142（2025 末）起强制 **Local Network Access (LNA)** 权限，发往 localhost 的请求被拦时
  fetch 静默失败（无细节）。扩展理论上凭 host_permissions 豁免，但 2026 版本行为收紧。
- 插件侧修复：`safeFetch` 统一加 `targetAddressSpace: 'local'`（官方推荐声明，需要授权时弹提示而非静默失败）；
  `normalizeApi` 规范化地址（漏写 http:// 会直接 fetch 失败）；popup 不再自己 fetch，统一走 background 的 DS_PING。
- 用户侧解法（按顺序）：① 核对弹窗地址 http://localhost:3101 ② 在普通标签页打开
  http://localhost:3101/pricing/extension/pending?limit=1 应显示 JSON ③ chrome://settings/content/localNetworkAccess
  允许 ④ chrome://flags/#local-network-access-check → Disabled → 重启 Chrome（M152 前有效）。

## 09:25 LNA 终极绕过：localhost 中继（v1.1.0）
- 昨晚的 targetAddressSpace 声明不够：扩展的 service worker **无法触发 LNA 授权弹窗**（Chrome 限制），被拦就是静默失败。
- 方案：利用 Chrome 对「本地→本地」请求的 LNA 豁免 —— safeFetch 直连失败时，自动在
  **localhost:3100（ds 前端）的标签页**里用 chrome.scripting.executeScript 执行 fetch 到 3101。
  - 3100 在后端 CORS 白名单（FRONTEND_URL 默认值），跨端口 CORS 已 curl 验证通过
  - 中继标签 active:false 放后台，按 url pattern 查找复用
  - manifest host_permissions 增加 3100（v1.0.0→1.1.0），**改了 manifest 必须刷新插件**
- 以后凡是「扩展连不上本机服务」的问题，先想到 LNA，用 localhost 页面做中继是最稳解法。

## 09:30 真相：不是 LNA，是地址填错
- 用户把插件地址填成了 http://localhost:3100（前端）→ /pricing/extension/* 404。
- **能收到 404 说明扩展→localhost 的 fetch 是通的，Chrome 并没有拦**（昨晚的 Failed to fetch 大概率发生在我重启服务的空窗期）。
- 复现验证：3101 返回 200，3100 同路径返回 404。
- DS_PING 加了防呆：404 时明确提示"3100 是前端页面，请改填后端 3101"。
- 教训：排查"连不上"要先区分「网络层失败(Failed to fetch)」vs「收到 HTTP 错误(404/500)」——后者网络是通的。

## 09:30 popup 输入框被轮询覆盖的 bug
- 症状：用户在地址框输入 3101，会"自动变回"3100，保存也无效。
- 根因：refresh() 每 2s 执行 `$('api').value = r.api`，无条件覆盖输入框 → 用户输入被打断冲掉，
  点保存时框里已是旧值，等于把 3100 又存了一遍。
- 修复：`document.activeElement !== $('api')` 时才更新输入框；保存后 blur + 按钮反馈"已保存 ✓"。
- 教训：任何定时刷新 UI 的代码，都不要碰正在被用户编辑的控件。
