# 2026-10-09

## 服务器模式下线「浏览器 Agent 一键核价（图搜）」
- 现象：在 http://ozon.qinxianty.com/pricing?sku=2839100571 点「开始图搜（用我的 Chrome）」报 `agent 异常退出（code 1）`。
- 定位（两层）：
  ① 直接原因：`deploy.sh` 的 tar 排除了 node_modules，服务器上 `scripts/browser-agent/node_modules` 不存在 → 缺 `puppeteer-core` → node 启动即 `ERR_MODULE_NOT_FOUND` → exit 1。
  ② 根本原因（修了也没用）：功能靠后端进程连 `127.0.0.1:9222`，服务器上的回环地址是服务器自己，连不到用户本机 Chrome；且无头环境 1688 图搜返回空。
- 处理（按用户要求「先下掉」）：加总开关 `AGENT_ENABLED`（默认 true 供本机用）。
  - `backend/src/modules/agent/agent.service.ts`：`enabled` getter；`findCandidates` 关闭时抛明确 400；`doctor` 返回 `enabled`（关闭时不探测 9222）。
  - `frontend/src/app/pricing/Workbench.tsx`：新增 `agentEnabled` state，卡片 `display: agentEnabled===false ? 'none' : undefined`。
  - `deploy.sh`：服务器生成的 `backend/.env` 加 `AGENT_ENABLED=false`（**必须写在 deploy.sh 里**，因为每次 deploy 都会重建 server 端 .env，手改会被覆盖）。
- 验证：线上 `/agent/doctor` = `{"enabled":false,...}`；`/agent/find` 返回「浏览器 Agent 已在当前部署中关闭…」；连用户 Chrome 真机打开线上页面确认卡片 `display:none`、页面其余正常。
- 本机版不受影响（本地 `.env` 无该变量 → 默认 true）。

## 服务器模式 1688 自动化技术方案（只出方案，未开工）
- 用户问「如何在服务器完成 1688 找货/核价/保存的自动化」，产出 `docs/服务器模式1688找货核价-技术方案.md`。
- 关键实测（推翻了"只是图搜不行"的判断）：线上 `cookie-status` → hasCookie:false；`POST /api/pricing/sourcing/offer` → 400 `ALI_RISK/IP_BAN`，msg「1688 把云服务器的机房 IP 段整体拉黑了（cloud_ip_bl），连滑块都不给」。
  ⇒ **服务器直连 1688 全废**（含手工贴链接抓价，这是线上现存问题）；段级封禁，换 IP/UA/cookie 无效。
- 能力拆解：①取图 ✅ ②图搜 ❌ ③抓价 ❌ ④算价 ✅ ⑤落库 ✅ —— 卡点只在 ②③ 两步（需出网访问 1688）。
- 方案对比：A 云控本机浏览器（推荐，1–1.5 天）、B SSH 隧道（临时）、C 服务器无头+住宅代理（有月费、仍可能触发滑块）、D 1688 官方开放 API（长期正解，需企业资质）、E 半自动（现状）。
- 方案 A 要点：本机 daemon **主动外连**服务器（NAT 后服务器连不进来）；用**长轮询**而非 WebSocket（站点是 http，无需改 nginx；图搜本就 20–40s，2s 轮询无感）；新增 `AgentTask` 表 + `POST /agent/tasks`、`GET /agent/tasks/poll`、`POST /:id/result`、`POST /:id/choose`；daemon 用 CDP 读本机 Chrome 的 `localStorage.ds_token` 自动登录；图片必须下载到本机临时文件再 `uploadFile`（CDP 传的是本机路径，顺带解决"服务器路径本机不存在"问题）；抓价也改由 daemon DOM 抓（服务器 IP 被封）。
- 落地计划 P0（修线上抓价报错文案/引导）→ P1（长轮询通道+daemon+前端）→ P2（自动选同款 Top1 + launchd 自启 + 批量）→ P3（升级 WebSocket / daemon 一键下载包）。
- 待运营确认：是否允许「自动选同款 Top1」跳过人工挑选（P1 保留人工，P2 再开）。

## 商品库汇率偏高修正（0.0862 → 0.0788）
- 用户发现商品库 61.88 ₽ 显示 ¥5.33，质疑不对。
- 查证真实汇率（央行 2026-10-09 中间价）：1 元 = 12.6873 ₽ → **1 ₽ = 0.0788**；中行折算价 0.0785。
- 系统里原本有**三套汇率**：① 商品库显示用 `settings.exchangeRate = 0.0862`（≈11.6 ₽/元，偏高 9.4%）；② 插件采集算 `priceCny` 写死 `RUB_TO_CNY = 0.08`；③ 真实 0.0788。① 和 ② 互不一致。
- 根因位置：`frontend/src/app/products/page.tsx:302` `cny = Number(p.price) * rate`，rate 来自 `GET /pricing/settings`；插件 `rules-lib.js:18`。
- **关键：`exchangeRate` 是全局定价参数**（`pricing.service.ts:240` 的 `rubToCny`/`cnyToRub`），影响售价换算与利润结论，属业务口径 → 请示用户后改为央行中间价。
- 改动：① 线上 `PATCH /pricing/settings {exchangeRate:0.0788, rubPerCny:12.69}`；② 统一硬编码兜底 0.0862→0.0788（后端 `pricing.service.ts:709` + 前端 `products/page.tsx`、`pricing/records/page.tsx`、`pricing/Workbench.tsx` 共 8 处）；③ 插件 `RUB_TO_CNY` 0.08→0.0788，`manifest.json` 1.7.0→1.7.1。
- 已存的定价记录保存了当时的汇率快照，不受影响；只有新定价用新汇率。

## 「跟卖价(₽)」实为人民币：products.price 币种混存（查实，未修）
- 用户截图指出 Ozon 商品页「63.57 ¥ 是人民币、789 是卢布」，问库里「跟卖价(₽)」是否存错。→ **是，存错了：存的是人民币值，字段/展示却当卢布用。**
- 证据链：
  ① 线上库 1011 条商品按 raw.priceSymbol 分组：`¥` 608 条（price 均值 52.6，5–4336）｜`₽` 132 条（均值 602）｜无符号 271 条（均值 1822）。两组量级差 11.4 倍 ≈ 人民币/卢布汇率 → 不同币种。
  ② 逐条验证 4 个 SKU：库内 price ÷ 0.0788 ≈ 该商品页面卢布价（785↔789、258↔262、198↔199、455↔464），4/4 命中。
  ③ 时间分布：10-06（244）、10-07（171）几乎全 ¥ → 是**当前正在发生**，不是历史遗留。
  ④ 采集来源都是 `from:'list'`（Ozon「中国商品」highlight 列表页）。
- 根因：插件 `collector-lib.js` 选价优先取 class 含 `tsHeadline` 且含货币符号的文本；Ozon 把卡片价渲染成 ¥ 时就把 ¥ 数值存进 price，仅把符号留档到 `raw.priceSymbol`。插件注释 + `sourcing.service.ts:1818` 都假设「符号变 ¥ 但数值仍是卢布量级」——**该假设被证伪**。`products.currency` 恒为 RUB（默认值），不可用。
- 实测澄清：今天在同一个卡片上复现插件选价逻辑，得到的是正确的 `789 ₽`（tsHeadline 元素就是 "789 ₽"）→ 说明**页面渲染成 ¥ 的那些时刻**才是出错条件。
- 影响：跟卖价列、定价高于跟卖价标红/筛选、商品库「价格(¥)」列、Excel 导出的跟卖价列。
- 另：用户先前问的「商品库 61,88 ₽ = ¥5.33」就是本 bug 的表象；当时只把汇率 0.0862→0.0788（另一个真问题），**没解决这个症状**（现在会显示 ¥4.88，仍错）。
- 临时调试脚本已挪到 `/tmp/ds-dbg-mjs/`；遗留的调试标签页已关闭。待用户选定修复方案（读时归一 / 写时归一+历史迁移 / 只修展示）。
