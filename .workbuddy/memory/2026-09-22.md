# 2026-09-22 补信息抓不到类目/价格 的排查与修复（承接 09-21）

## 类目一直抓不到的根因（实测确认）
- Ozon 商品页的类目面包屑挂在 **`[data-widget="breadCrumbs"]`**（驼峰、大写 C）。我原先写的选择器是
  `[data-widget*="breadcrumb"]`（全小写）→ 永远匹配不上（"breadCrumbs" 里的 "Crumb" 是大写 C）。
  实测：`[data-widget*="bread"]` 命中 1 个，其 innerText = "Дом и сад\nТовары для праздников\n…"，4 个 `a`。
- 而且面包屑是 **JS 延迟渲染**的：实测导航后 0ms 时 `bodyLen=0`、面包屑为空，3~5 秒（有时十几秒）才出现。
  只等 `location.href` 跳转就开抓，只能拿到服务端渲染的 meta（title / og:image / price），类目和评论永远读不到。
- 修复：新增 `WAIT_READY_JS`（等 `[data-widget*="bread"] a` / `[class*="breadcrumb"] a` 出现，上限 8 秒、间隔 500ms，
  等不到也继续，不会像旧版那样死等 60 秒）；面包屑选择器改为同时覆盖 `bread`/`Bread`/`breadcrumb`/`Breadcrumb`。

## 价格
- 价格来自 JSON-LD 的 `offers.price`（实测 389、1216、266 都能拿到）。另加了兜底：
  `product:price:amount` meta → 正文正则 `(\d[\d\s\u00a0]*)[\s\u00a0]*₽`。
- 实测之前价格为空的商品（5733070101）补信息后 price=266.00，接口返回 `{"ok":true,"fields":["title","categoryPath","price","imageUrl","reviewsCount"]}`，**耗时 9.3 秒**（旧版 60 秒+）。
- 商品列表页原先**根本没有价格列**，已新增「价格」列（`dataIndex:'price'`，右对齐、可排序、渲染成 `1 216 ₽`），
  `scroll.x` 1700→1800。后端 `products.service.ts` 的 `SORTABLE` 本来就含 price，接口也一直返回 price。

## 其它顺带修的
- 评论数正则补上不换行空格：Ozon 数字里用 `\u00a0`，原 `[\d\s]*` 匹配不到 → 改为 `[\d\s\u00a0]*`。
  另：正文含「Нет отзывов」时直接置 `reviewsCount=0`（区分"没有评论"和"没抓到"）。
- `withPage` 里的 1688 登录检测改为只试 1 次（`ev(expr, 1)`）：它是给 1688 用的，Ozon 页面恒为 false，
  但在重页面上可能超时，默认重试 3 次 × 12 秒 = 最坏白卡 36 秒。
- 批量补信息的筛选条件再调整：只按**稳定能补到**的字段挑（categoryPath / imageUrl / price / reviewsCount），
  brand、rating 只"顺带补"不参与筛选 —— 这批白牌商品 Ozon 上 brand 是空串、正文「Нет отзывов」，
  若按 brand 筛选会被反复挑中、永远补不完。

## 中实跨境ERP「闪电采集」插件 v3.8.6 源码分析（源码在 ~/Downloads/sd-plugin-3.8.6）
- manifest V3，名叫「闪电采集」。content.js（1.2MB）注入 ozon.ru / seller.ozon.ru / 1688.com；
  seller-bridge.js 注入 seller.ozon.ru；background.js 是 service worker。
- **三层数据来源**：
  ① Ozon 页面公开 DOM/CSS（标题、价格、主图等基础信息）
  ② **Ozon 卖家后台分析接口** `/api/site/seller-analytics/what_to_sell/data/v3`
     ← 这才是 月销/加购率/退货率/广告占比/上架天 的真正来源，**必须有 Ozon 卖家账号登录态**
     （插件通过 `/admin-api/ozon/extension/seller-cookie/bind` 绑定卖家 cookie）
  ③ 中实 ERP 云端 `https://ssyk.shanshangnet.com/admin-api/ozon/extension/*`（采集计划下发 collect-plan、
     SKU 缓存 sku-cache、原始采集数据上报 browser-collect-raw）+ 本机桌面端
     `http://127.0.0.1:8765/product-detail`（POST {skuid}，desktopAppUrl 存在 chrome.storage.local）
- 字段与 ds 完全同源（都在插件源码里出现过）：soldCount / soldSum / convToCartPdp / convToCartSearch /
  cancelRate / drr / daysWithTrafarets / createDays / daysInPromo。
- **数据如何暴露出来（关键）**：插件把商品卡渲染进页面，容器为
  `.s2-widget-card` / `.s2-tile-host` / `#s2-pdp-real-price-card` / `[data-s2-ozon-sku]`；
  每个字段是一行 `[data-s2-field-key="<字段名>"]` + 值在 `.s2-widget-value`。
  内部状态是 `{skuId, status, cardData:{...}, rows, offers, visibleFieldKeys}`。
- **重要纠正**：ds 旧代码扫的 `data-s2-card-data-json` 在 v3.8.6 里**根本不存在**（只有 data-s2-field-key /
  data-s2-ozon-sku / data-s2-widget 等 UI 标记）—— 这就是当初"插件数据读不到"的原因之一。
- **接入本系统的三条路**（按性价比排序）：
  1. 读商品卡 DOM：`[data-s2-field-key="soldCount"] .s2-widget-value`（不用改插件，但依赖其 UI 结构）
  2. 拦截网络响应：CDP Network 捕获 `what_to_sell/data/v3`、`product-card/sku-cache` 的响应 JSON（字段最全、最稳）
  3. 改「站点域名」指向自己后端：插件 `${base}/admin-api/...` 的 base 可配置（UI 里有"站点域名"输入框，
     manifest 有 localhost 权限），只需实现 check-login / browser-collect-raw 等少数端点即可接收原始上报；
     但要复刻登录与会员校验，偏 hack。
- **硬前提**：月销这类指标必须有 Ozon 卖家账号登录态，光装插件拿不到。

## 23:50 插件连不通的两个坑（已修）
- **坑1：Chrome Private Network Access (PNA)**。插件（chrome-extension:// 源）请求 localhost 属于访问私有网络，
  除普通 CORS 外还要求服务端返回 `Access-Control-Allow-Private-Network: true`，否则浏览器直接按网络失败处理
  → 插件里一堆 "Failed to fetch"，但 curl 完全正常（curl 既不检查 CORS 也不做 PNA）。
  修法：`main.ts` 在 `enableCors` **之前**挂一个中间件设该头（放前面预检 OPTIONS 才带得上）。
- **坑2：「当前页不是 Ozon 商品页」误判**。原先死板匹配 `/ozon.ru/product//`，用户从搜索页/带参详情页/其它 ozon 域名过来都被拒。
  修法：放宽为「hostname 含 ozon.ru|com|kz|by 就试采」，真实门槛放在「能否从 URL 解析出 sku」和「是否采到数据」。
- 附带：`background.js` 加 `safeFetch`，把网络层失败翻译成中文提示（原来是干巴巴的 Failed to fetch）。
- 插件改代码后必须在 chrome://extensions 点刷新（↻）才会生效。
