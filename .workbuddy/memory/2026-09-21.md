## 21:25 追加：浏览器接管功能在服务器上做优雅降级

- 现象：在 /collect 点「启动/检查浏览器」报错 `rsync ... change_dir "/root/Library/Application Support/Google/Chrome" failed`。根因：`BrowserService` 是 macOS 桌面专属——复制本机 Chrome 配置 + `open` 启动带调试端口的 Chrome（依赖 GUI + 已登录插件）。服务器无 GUI/Chrome，该目录不存在 → 崩。
- 修复：在 `backend/src/modules/browser/browser.service.ts` 加 `isSupported` getter（`process.platform === 'darwin'`），`status()` 与 `ensure()` 在非 macOS 时直接返回友好中文提示（ok:false / supported:false），不再执行 rsync。`frontend/src/app/collect/page.tsx` 加 Alert 横幅：`browser?.supported === false` 时显示“浏览器接管功能当前不可用”。
- 验证：`GET /api/browser/status` 与 `POST /api/browser/start` 经 80 端口均返回清晰提示、后端错误日志干净。
- 结论：采集/浏览器接管**必须在用户 Mac 本机运行**（要的是装了插件、登了号的 Chrome）；服务器仅跑 API + Web + 数据。此功能非部署缺陷，是架构限制。
- 关键代码事实：`BrowserService.portUp()` 连的是 `127.0.0.1:9222`（host 写死回环），`chromeBin` 写死 `/Applications/Google Chrome.app/...`。即采集后端必须与 Chrome 同机（= Mac）。服务器无 GUI/Chrome → 端口起不来 → 采集任务报「调试端口未就绪」。
- **把采集数据送进服务器库的推荐做法**：Mac 本地跑后端+Chrome 采集，开 SSH 隧道 `ssh -L 3306:127.0.0.1:3306 root@114.132.99.141`，Mac 后端 DATABASE_URL 改 `mysql://root:<pw>@127.0.0.1:3306/ds`（服务器 MySQL 已 bind 127.0.0.1，只能经隧道访问）。采集即写服务器库，前端立即可见。

## 21:55 追加：本地一键部署脚本 deploy.sh（tar 直推，已实测跑通）

- 因服务器访问 GitHub 不稳（clone 断流），最终放弃 git clone 方案，改用**本地 tar 直推**：`deploy.sh` 在项目根目录，本地 `./deploy.sh` 即完成「打包源码 → SSH 直传 /root/ds → 重建 env/ecosystem → 构建前后端 → prisma db push（幂等）→ pm2 重启 → 健康检查」。
- 关键设计（踩坑后定型）：

  - tar 排除：`node_modules .git .next dist run *.sql .env .env.local */.env */.env.local .workbuddy deploy.sh`。
  - 服务器专属文件（ecosystem.config.js、backend/.env、frontend/.env.local）脚本内自动重建；DB 密码读 `/root/.ds_db_root.txt`；JWT 持久化到 `/root/.ds_jwt.txt`（首次随机生成，重部署复用，登录态不失效）。
  - 前端 `NEXT_PUBLIC_API_URL` 写死 `http://114.132.99.141/api`（80 端口 nginx 反代）。
- 实测结果：TRANSFER_DONE（638 文件）、前后端构建成功、pm2 双 online、健康检查 `frontend / -> 200`、`/api/auth/profile -> 401`。
- 用法：本地改完代码 → `./deploy.sh`（无需手动 push GitHub，脚本直接传本地工作区）。之后重部署即跑此脚本。

## 22:51 追加：采集/补信息必须跑本地栈 + 服务器库实为空的拓扑事实 + 新增「补商品信息」功能

- **重要拓扑事实**：服务器 MySQL（114.132.99.141）`products` 表 `total:0`，是空的。用户那 112 条采集商品（task #20 成功）写在**本机 Mac 的 MySQL** 里——因为采集需要 Chrome（调试端口 127.0.0.1:9222），只能由本机后端触发，数据落本地库。验证：`curl 服务器 /api/products?pageSize=1` 返回 `{"list":[],"total":0}`；`POST /api/pricing/sourcing/product-info` 对已知 sku 返回「商品不存在」。
- 所以「补商品信息 / 采集」这类依赖 Chrome 的动作，**必须在本机栈（localhost:3100/3101 + 本机 MySQL + 本机 Chrome）触发**，服务器部署只是 app 副本（无数据、无 Chrome）。
- 若想让服务器也显示采集/补信息后的数据，两条路：(a) 本机后端 DATABASE_URL 经 SSH 隧道指向服务器 MySQL（采集/补信息直写服务器库）；(b) 把本机库迁移到服务器。否则服务器永远是空壳 demo。
- 本次新增「补商品信息」功能（替代原「补主图」）：后端 `SourcingService.enrichProductInfo(sku)` / `enrichMissingProducts(limit)`，打开 Ozon 商品详情页，`PROBE_JS` 通用合并页面所有 `data-s2*` 注入的 JSON（插件完整数据）+ 公开 DOM 兜底（品牌/类目面包屑/评论数/发货 FBS-FBO/og:image），映射到 Product 全字段 upsert（只更新非空字段，绝不覆盖已有好值）+ 写 ProductMetric。接口 `POST /pricing/products/fill-info`（批量）与 `POST /pricing/sourcing/product-info`（单条）。前端商品库页「补商品主图」→「补商品信息」、「补主图」→「补信息」。
- **本机 stop/start 重启失败的修复（重点排查经验）**：现象是 `stop.sh` 报「端口 3101 被非本项目进程占用 (PID 44731) node dist/main」不愿杀，而 `start.sh` 又打印「✔ 后端已启动」——**假成功**。根因：PID 44731 是从旧路径启动的残留后端，其 cwd 为 `/Users/huanghui/.Trash/ds/backend`（项目当年放 Trash 里跑过，后来迁到 `Documents/huanghui/github/ds`），而 `port-guard.sh`/`stop.sh` 原先只按**当前项目绝对路径**匹配，路径变了就判定为「非本项目」，永不清理 → 旧进程继续占 3101 → 新后端 bind 失败静默退出，而 `wait_port` 只测「端口在监听」看到的是旧进程，于是假成功。
- 修复（已写入仓库）：新增 `scripts/_ds_proc.sh` 提供 `is_ds_proc <pid>`，按 **cwd 以 `ds/backend` 或 `ds/frontend` 结尾**（不论父路径，兼容迁移/Trash）优先判定，再兜底当前 `$ROOT` 路径与 argv 特征（`dist/main`/`next-server`/`npm run start`）。`port-guard.sh` 与 `stop.sh` 均改为复用它。同时 `start.sh`：free-ports 之后**复核端口确实空闲**才启动（否则明确报错退出，不再静默撞端口）；就绪检查从「只测端口监听」改为「端口起来了 + 刚启动的 PID 仍存活」，并 tail 日志。
- 注意：`lsof -nP -iTCP:3101 -sTCP:LISTEN` 是判活/判占位的可靠手段；本沙箱里后台进程会随工具调用结束被回收、curl 受 HTTP 代理干扰返回 502（**用 `curl --noproxy '*'` 可绕过**），跨调用验证不可靠，应在**同一次 bash 调用内**启动并验证。
- **第二个坑（前端改了源码但页面没变）**：本机 3100 跑的是**生产模式** `npm run start`，服务的是 `.next` 产物而非源码。原 `start.sh` 只在「产物不存在」时才 build，而 `.next/BUILD_ID` 只要存在（哪怕比源码旧 22 小时）就跳过编译 → **重启永远跑旧代码**，用户会误以为"没重启生效"。排查手法：比对 `frontend/src/app/...tsx` 与 `frontend/.next/BUILD_ID` 的 mtime；产物是否真含新文案用 `grep -rl "新文案" .next/` 确认（本次即"补商品信息" vs 旧"补主图"）。
- **「补商品信息」改为纯公开抓取（用户已卸载 ERP 插件）**：旧实现 `PROBE_JS` 依赖「中实跨境ERP」插件注入的 `data-s2*` 属性，且 `enrichProductInfo` 会**死等插件注入最多 60 秒/个商品**（`while(Date.now()<deadline)`，每轮 `sleep(2500)`），插件卸载后这个等待永不满足 → 每个商品白等 60 秒，这是「补全很慢」的真正主因；另外 `PROBE_JS` 遍历**全部元素的全部属性**也很重。
- 新实现 `PUBLIC_PROBE_JS`（`sourcing.service.ts` 顶部常量，模板字面量末尾 `.replace(/\s*\n\s*/g,' ')` 压成单行给 CDP）：三级取数 ① `script[type="application/ld+json"]` 的 Product 结构化数据（title/brand/image/price/rating/reviewsCount，SSR 自带最可靠）② og/meta 兜底 ③ 公开 DOM（h1、`a[href*="/brand/"]`、面包屑、正文正则 `(\d[\d\s]*)\s*(отзыв|отзыва|отзывов)`、`\b(FBS|FBO|rFBS)\b`、`a[href*="/seller/"]`）。不再等插件，页面加载完读一次（最多重试 3 次、间隔 700ms）。
